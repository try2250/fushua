## 1. 概述与核心理念

### 1.1 为什么要代码审查？

代码审查不是找茬，而是**知识共享、质量保障、风险防控**的团队实践。好的审查让每个人都能写出更好的代码。

### 1.2 核心理念

| 原则 | 说明 |
|------|------|
| **教而非判** | 每条评论都是一次教学机会，解释"为什么" |
| **具体而非笼统** | "第42行存在SQL注入风险" 而非 "安全问题" |
| **建议而非命令** | "考虑使用X，因为Y" 而非 "改成X" |
| **优先级分明** | 用 🔴🟡💭 标记让作者知道什么必须改 |
| **一次完整反馈** | 一轮审查给出全部意见，不分批滴灌 |
| **称赞好代码** | 看到聪明的方案、干净的写法要指出来 |

### 1.3 什么必须审查？

- ✅ 所有 PR / MR 必须至少一人审查通过后才能合并
- ✅ Bug 修复 — 重点看是否真正修了根因
- ✅ 新功能 — 重点看设计、安全、测试
- ✅ 重构 — 重点看行为是否保持不变
- ✅ 配置变更 — 环境变量、数据库迁移、依赖变更

## 2. 审查维度与评分标准

每个 PR 从以下 7 个维度评估，每个维度 0-10 分：

### 2.1 功能正确性（权重 25%）

代码是否按预期工作？边界条件是否处理？

| 检查项 | 说明 |
|--------|------|
| 需求对齐 | 变更是否满足 PR 描述中的所有需求 |
| 边界条件 | null/空值/空列表/0/负数是否处理 |
| 状态机 | 状态流转是否完整，不允许的转换是否阻止 |
| 并发 | 是否有竞态条件？关键操作是否原子化 |
| 回归 | 是否可能破坏已有功能 |

### 2.2 安全性（权重 20%）

是否存在安全漏洞？

| 检查项 | Fushua 专项 |
|--------|------------|
| SQL 注入 | 所有查询必须通过 SQLAlchemy ORM 或参数化 |
| XSS 防护 | 模板变量是否正确转义；`|safe` 过滤器使用是否合理 |
| CSRF 保护 | 状态变更操作是否校验 CSRF Token |
| 认证授权 | 端点是否有正确的 `require_login`/`require_teacher`/`require_admin_role` |
| 输入校验 | 所有用户输入是否经过 `sanitize_input`/`parse_int` |
| 敏感数据 | 密码/Token/密钥是否明文出现在日志或响应中 |
| JWT 安全 | Token 过期时间是否合理；密钥是否来自环境变量 |

### 2.3 代码可维护性（权重 15%）

6个月后别人能看懂吗？

| 检查项 | Fushua 专项 |
|--------|------------|
| 命名 | 变量/函数/类名是否表达意图 |
| 函数长度 | 单函数是否超过 50 行（router handler 放宽至 80 行） |
| 文件大小 | 单文件是否超过 500 行？需不需要拆分？ |
| 重复代码 | 是否有可提取的公共逻辑 |
| 注释 | 复杂逻辑是否有解释；注释是否与代码一致 |
| 模块职责 | 路由层不应包含复杂业务逻辑，应委托给 Service 层 |

### 2.4 性能（权重 15%）

是否有明显性能问题？

| 检查项 | Fushua 专项 |
|--------|------------|
| N+1 查询 | 循环中是否有数据库查询；是否可用 joinedload/子查询 |
| 大数据量 | 列表接口是否有分页 `paginate()` |
| 索引 | 新增查询条件对应的数据库列是否有索引 |
| 缓存 | 频繁读取的配置/字典数据是否考虑缓存 |
| 连接管理 | 数据库 session 是否正确关闭 |

### 2.5 测试（权重 15%）

测试是否充分？

| 检查项 | 说明 |
|--------|------|
| 核心路径 | 正常流程是否有测试 |
| 边界条件 | 边界/异常是否有测试 |
| 权限 | 权限相关变更是否有跨角色测试 |
| 测试质量 | 测试是否独立、可重复、有意义的断言 |
| 测试命名 | 测试名是否描述场景：`test_<what>_<when>_<then>` |

### 2.6 类型安全（权重 5%）

类型注解是否完整准确？

| 检查项 | 说明 |
|--------|------|
| 函数签名 | 参数和返回值是否有类型注解 |
| Optional | 可能为 None 的值是否标注 Optional |
| Any 使用 | 是否不必要地使用 Any |

### 2.7 文档（权重 5%）

变更是否易于理解？

| 检查项 | 说明 |
|--------|------|
| PR 描述 | 是否说明了改了什么、为什么、怎么测 |
| 代码注释 | 复杂/非直观逻辑是否有注释 |
| API 文档 | 新增/修改的 API 端点是否有说明 |

## 3. 审查检查清单

### 3.1 快速检查（每 PR 必做）

```
□ git diff 浏览变更范围是否合理
□ 自动化检查（CI lint/test）是否通过
□ PR 描述是否清晰
□ 是否有明显的安全漏洞
□ 核心逻辑是否正确
```

### 3.2 完整检查（重要 PR）

```
安全性:
□ 无 SQL 注入（所有查询走 ORM/参数化）
□ 无 XSS（模板正确转义；|safe 使用安全）
□ 认证授权正确（depends 依赖注入已使用）
□ CSRF Token 校验（状态变更操作）
□ 输入经过 sanitize_input/parse_int
□ 密码/Token 未在日志/响应中泄露

功能正确性:
□ 正常流程覆盖
□ 边界条件处理（null/空/负数/超大值）
□ 错误情况有合适的 HTTP 状态码和消息
□ 权限隔离正确（跨班级、跨角色）

代码质量:
□ 命名清晰
□ 无超长函数（>50行 router handler 除外）
□ 无超长文件（>500行考虑拆分）
□ 业务逻辑在 Service 层而非 Router 层
□ 无重复代码可提取
□ 类型注解完整

性能:
□ 无 N+1 查询
□ 大数据集有分页
□ 循环外的查询已优化

测试:
□ 核心路径有测试
□ 边界条件有测试
□ 权限变更有多角色测试
□ 所有测试通过
```

## 4. 审查流程

### 4.1 流程总图

```
开发者                  审查者                  自动化
  │                       │                       │
  ├─ 创建 Feature 分支    │                       │
  ├─ 编码 + 自测          │                       │
  ├─ git push             │                       │
  │                       │                       ├─ CI: lint → test → build
  │                       │                       │   ↓ 失败则阻断
  ├─ 创建 PR ────────────→│                       │
  │                       ├─ 接收审查请求          │
  │                       ├─ 浏览变更              │
  │                       ├─ 逐文件审查            │
  │                       ├─ 填写审查报告          │
  │                       ├─ 提交评论 ────────────→│
  ├─ 收到评论              │                       │
  ├─ 逐条回复/修改         │                       │
  ├─ git push 更新         │                       │
  │                       ├─ 复查修改              │
  │                       ├─ Approve / Reject     │
  ├─ 合并到 main           │                       │
```

### 4.2 时间承诺

| PR 规模 | 期望审查响应时间 |
|---------|-----------------|
| 小型（<100行） | 4 工作小时内 |
| 中型（100-500行） | 1 工作日内 |
| 大型（500-1000行） | 2 工作日内 |
| 超大（>1000行） | 需拆分，建议先讨论设计方案 |

### 4.3 提交者职责

1. **自审**: 提交 PR 前自己过一遍 diff，确保没有遗留的调试代码、注释掉的代码
2. **测试**: 确保所有测试通过（本地运行 `pytest`）
3. **描述**: 写清楚：
   - 做了什么（What）
   - 为什么这样做（Why）
   - 怎么测试的（How to test）
   - 截图（UI 变更时）
4. **小 PR**: 尽量控制在 500 行以内
5. **响应**: 及时回复审查评论

### 4.4 审查者职责

1. **及时**: 在规定时间内完成审查
2. **完整**: 一轮给出所有意见，不分批滴灌
3. **优先级**: 用标记让作者知道轻重缓急
4. **善意**: 假设作者的意图是好的，评论针对代码而非人
5. **教育**: 解释"为什么"，而不只是"改成什么"
6. **称赞**: 好的代码要明确表扬

### 4.5 审查结果

| 结果 | 含义 |
|------|------|
| ✅ **Approve** | 代码可以合并，无阻塞问题 |
| 💬 **Comment** | 有问题需要讨论，但不阻塞合并 |
| ❌ **Request Changes** | 有必须修复的问题，修复后重新审查 |

## 5. 审查评论格式规范

### 5.1 优先级标记

| 标记 | 含义 | 必须修复？ |
|------|------|-----------|
| 🔴 **Blocker** | 安全漏洞、数据丢失、生产事故风险 | ✅ 是 |
| 🟡 **Suggestion** | 性能问题、可维护性问题、测试缺失 | 建议修 |
| 💭 **Nit** | 命名建议、风格优化、替代方案 | 不必修 |
| 👍 **Praise** | 写得好的地方 | — |

### 5.2 评论模板

```
🔴 **Blocker: [问题类型]**
[文件:行号] — [具体描述]

**为什么这是问题：** [影响和后果]

**建议方案：**
```python
# 好的写法
[代码示例]
```

**参考：** [相关文档链接]
```

### 5.3 评论示例

```
🔴 **Blocker: SQL 注入风险**
app/routers/student.py:142 — 用户输入直接拼接到 SQL 查询中

**为什么这是问题：** 攻击者可通过 name 参数注入恶意 SQL，例如：
`'; DROP TABLE users; --`

**建议方案：**
```python
# ❌ 当前
query = f"SELECT * FROM users WHERE name = '{name}'"

# ✅ 应该
user = db.query(User).filter(User.name == name).first()
```

**参考：** OWASP SQL Injection Prevention Cheat Sheet
```

```
🟡 **Suggestion: N+1 查询**
app/routers/teacher.py:89-95 — 在循环中逐条查询学生信息

**为什么这是问题：** 当班级有 50 个学生时会导致 51 次数据库查询。
使用 `joinedload` 可以降到 1 次查询。

**建议方案：**
```python
# ❌ 当前
assignments = db.query(Assignment).all()
for a in assignments:
    student = db.query(User).filter(User.id == a.student_id).first()

# ✅ 应该
assignments = db.query(Assignment).options(
    joinedload(Assignment.student)
).all()
```
```

```
💭 **Nit: 变量命名**
app/services/auth_service.py:23 — `x` 作为函数参数名不够清晰

**建议：** 考虑重命名为 `login_attempt_count` 以表达意图。
```

```
👍 **Praise: 干净的实现**
app/services/backup_service.py:45-67 — 备份逻辑写得很清晰，
事务边界处理得当，错误恢复机制完善。好代码！
```

## 7. 自动化工具配置

### 7.1 工具栈

| 工具 | 用途 | 配置文件 |
|------|------|---------|
| **Ruff** | Linting + 格式化（替代 Flake8/isort/Black） | `pyproject.toml [tool.ruff]` |
| **MyPy** | 静态类型检查（可选，逐步引入） | `pyproject.toml [tool.mypy]` |
| **pre-commit** | Git 提交前自动检查 | `.pre-commit-config.yaml` |
| **pytest** | 测试运行 | `pytest.ini` |

### 7.2 本地使用

```bash
# 安装开发依赖
pip install ruff pre-commit

# 安装 Git Hooks（首次）
pre-commit install

# 手动运行 lint
ruff check app/ tests/

# 手动格式化
ruff format app/ tests/

# 运行测试
pytest tests/ -v --tb=short
```

### 7.3 CI 自动化

CI 流水线包含以下步骤（按顺序）：

```
1. ruff check  → Lint 检查
2. ruff format --check  → 格式检查
3. pytest  → 运行测试
4. (未来) mypy  → 类型检查
```

## 8. Fushua 项目专项规范

### 8.1 架构分层约定

```
请求 → Router (路由+参数提取)
     → Service (业务逻辑)
     → Model (数据库操作)
     → Response
```

- **Router 层**：只做参数提取、调用 Service、渲染模板/返回 JSON。不应包含 SQLAlchemy 查询。
- **Service 层**：纯业务逻辑，操作数据库，返回领域对象。方法签名应完整类型注解。
- **Schema 层**：Pydantic 模型，用于 API 的请求/响应序列化。与数据库 Model 分离。

### 8.2 安全专项

| 规则 | 说明 |
|------|------|
| **CSRF Token** | 所有 POST/PUT/DELETE 页面路由必须调用 `validate_csrf_async(request)` |
| **输入清理** | 所有用户输入必须通过 `sanitize_input(value, max_length=N)` |
| **整数解析** | 数值参数用 `parse_int(value, min_value=N)` |
| **分页** | 列表接口用 `paginate(query, page_num, per_page=N)` |
| **认证依赖** | 用 `require_login`/`require_teacher`/`require_admin_role` 装饰端点 |
| **密码** | 永远不要明文存储或记录到日志；使用 bcrypt 哈希 |
| **JWT** | Token 过期时间 ≤ 24 小时；密钥来自环境变量 `SECRET_KEY` |

### 8.3 数据库操作

| 规则 | 说明 |
|------|------|
| **ORM 优先** | 所有查询使用 SQLAlchemy ORM，禁止字符串拼接 SQL |
| **Session 管理** | 通过 `Depends(get_db)` 获取 session，不要手动管理 |
| **N+1 预防** | 关联查询用 `joinedload()`/`selectinload()` |
| **批量操作** | 批量插入/更新用 `bulk_insert_mappings`/`bulk_update_mappings` |
| **事务** | 多步写操作确保在同一事务内；异常时回滚 |

### 8.4 文件大小红线

| 文件 | 当前大小 | 目标 | 行动 |
|------|---------|------|------|
| `app/routers/teacher.py` | 92KB (~2500行) | 拆分为 3-4 个模块 | 高优先级 |
| `app/routers/admin.py` | 40KB (~1100行) | 拆分为 2-3 个模块 | 高优先级 |
| `app/routers/student.py` | 34KB (~950行) | 拆分为 2 个模块 | 中优先级 |
| `app/models.py` | 20KB (~550行) | 按领域拆分 model 文件 | 低优先级 |

拆分策略：
```
app/routers/teacher/
├── __init__.py          # 路由注册
├── questions.py         # 题目管理相关路由
├── assignments.py       # 作业管理相关路由
└── class_management.py  # 班级管理相关路由
```

### 8.5 测试规范

| 规则 | 说明 |
|------|------|
| **命名** | `test_<被测模块>_<场景>_<预期结果>` |
| **独立** | 每个测试独立创建和清理数据，不依赖执行顺序 |
| **数据库** | 使用 `conftest.py` 中的 fixtures 管理测试数据库 |
| **权限测试** | 新功能涉及权限检查时，测试至少覆盖：本人、同角色他人、低权限角色 |
| **API 测试** | API 测试使用 `TestClient`，验证状态码和响应结构 |

### 8.6 双认证系统注意事项

项目同时存在 **Session 认证**（页面路由）和 **JWT 认证**（API `/api/v1`）：

- 页面路由用 `app/auth.py` 的 `require_login` / `require_teacher` / `require_admin_role`
- API 路由用 `app/core/deps.py` 的 `get_current_user`
- **不要混用**：不要在页面路由中使用 JWT 验证，反之亦然
- 新增认证逻辑时，先确认应归入哪个系统

## 9. 附录：常见反模式

### 9.1 Python/FastAPI 反模式

| 反模式 | 问题 | 正确做法 |
|--------|------|---------|
| `except:` 裸异常 | 捕获了 KeyboardInterrupt/SystemExit | 捕获具体异常：`except ValueError:` |
| `except Exception: pass` | 静默吞掉错误 | 至少记录日志：`logger.exception(...)` |
| 在 Router 中直接写 SQL | 破坏分层、难以测试 | 移到 Service 层 |
| 循环中的数据库查询 | N+1 问题 | 使用 joinedload 或批量查询 |
| 密码硬编码 | 安全风险 | 从环境变量读取 |
| `import *` | 污染命名空间 | 显式导入或用 `__all__` |
| 字符串拼接路径 | 跨平台问题、注入风险 | 使用 `os.path.join` 或 `pathlib` |
| 过大的 try 块 | 错误来源不明确 | 只包裹可能抛出异常的代码 |

### 9.2 SQLAlchemy 反模式

| 反模式 | 问题 | 正确做法 |
|--------|------|---------|
| `db.query(Model).all()` 然后 Python 过滤 | 全表扫描 | 用 `.filter()` 在数据库侧过滤 |
| 忘记 `.first()` 调用后判空 | AttributeError | `if result is None: raise HTTPException(404)` |
| Session 手动 `commit()` 后不处理异常 | 数据不一致 | 使用 try/except 回滚 |
| `Model.query` 旧式 API | 与 FastAPI Depends 不兼容 | 使用 `db.query(Model)` |

### 9.3 安全反模式

| 反模式 | 正确做法 |
|--------|---------|
| 前端校验代替后端校验 | 必须在后端再校验一次 |
| 在 URL 中传递敏感参数 | 用 POST body 或 Header |
| `|safe` 用于用户输入 | 只在确保内容已转义时使用 |
| 错误信息暴露内部细节 | 对外用通用错误消息，内部记详细日志 |
