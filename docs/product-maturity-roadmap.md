# 付刷产品成熟化优化规划

本文档面向“从可部署 MVP 走向可长期服务真实班级的成熟产品”。规划顺序按风险优先级排列：先修数据隔离与安全，再补运维保障，最后做体验、运营和商业化能力。

## 当前判断

当前项目已经具备基础刷题、题库、班级、作业、错题、统计、部署配置和测试基础，适合小范围试跑。

但若要正式给真实教师和学生长期使用，还需要补齐以下成熟产品能力：

- 多教师、多班级的数据隔离。
- 作业、题库、学生、统计的权限边界。
- 数据备份、恢复、监控、告警。
- 管理员后台与运营工具。
- 隐私政策、未成年人数据处理说明、账号与数据删除机制。
- 自动化测试、自动部署和发布回滚流程。

## 执行原则

- 先保数据安全，再扩功能。
- 每个阶段都必须有验收标准和回归测试。
- 不做大而全重构，优先沿用现有 FastAPI + Jinja2 + SQLAlchemy 结构。
- 每次上线前先在 Render 预览或测试数据库跑迁移。
- 重要数据结构改动必须配套 Alembic 迁移和测试。

## 阶段 0：上线稳定性基线

目标：确保当前 Render 部署能稳定跑起来，并能复现构建、迁移、启动全过程。

### Step 0.1 确认 Render 部署成功

操作：

- 在 Render 重新部署最新 `main`。
- 确认构建阶段 `pip install -r requirements.txt` 成功。
- 确认启动阶段 `alembic upgrade head` 成功。
- 访问 `/health` 返回 `{"status":"ok"}`。
- 打开首页、注册页、登录页、题库浏览页。

验收标准：

- Render 服务状态为 Live。
- `/health` 正常。
- 首页无 500。
- 数据库中存在 `users`、`questions`、`class_groups`、`site_configs` 等表。

### Step 0.2 固化部署检查清单

新增或整理文档：

- `docs/deploy-checklist.md`

内容应包括：

- GitHub 最新提交。
- Render 服务名。
- Render 数据库名。
- 必填环境变量。
- 部署后访问地址。
- 首次教师邀请码。
- 常见失败处理：依赖安装失败、迁移失败、启动失败。

验收标准：

- 新成员能按文档独立完成一次部署。

## 阶段 1：权限隔离与数据安全

目标：修复正式上线前最关键的安全问题，避免不同教师、班级、学生之间互相看到或操作数据。

### Step 1.1 明确数据归属规则

需要确定以下规则：

- 教师只能管理自己创建的班级。
- 学生只能属于一个主班级，后续如要支持多班级，需要独立设计。
- 作业必须绑定一个班级，不能全站可见。
- 教师只能用自己创建的题目创建作业。
- 题库属于创建者，教师不能把题目挂到别人的题库。
- 教师只能查看自己班级学生的数据。
- 管理员可以跨教师查看和处理数据，但必须有明确入口和审计记录。

建议数据结构：

- `assignments.class_id`
- `assignments.created_by`
- `questions.created_by`
- `question_banks.created_by`
- `class_groups.created_by`
- `users.class_id`
- `class_members.class_id + user_id`

验收标准：

- 文档中明确每张核心表的归属字段。
- 每个跨用户访问入口都有权限判断规则。

### Step 1.2 修复教师查看学生详情越权

涉及文件：

- `app/routers/teacher.py`
- `tests/test_teacher_permissions.py`

当前风险：

- `/teacher/students/{student_id}` 只判断当前用户是教师，没有判断学生是否属于该教师班级。
- `/teacher/students/{student_id}/export/pdf` 同样存在风险。

实现步骤：

1. 新增 helper：`teacher_owns_student(db, teacher_id, student_id)`。
2. 查询当前教师创建的班级。
3. 通过 `ClassMember` 判断学生是否在这些班级里。
4. 不属于则返回 404 或 403。
5. 学生详情统计只展示该教师相关题目或该班级范围内的数据。
6. PDF 导出复用同一个权限 helper。

测试用例：

- 教师 A 可以查看自己班级学生。
- 教师 A 不能查看教师 B 班级学生。
- 教师 A 不能导出教师 B 学生 PDF。
- 管理员例外规则如暂未实现，应禁止跨班查看。

验收标准：

- 猜测其他学生 id 无法看到详情。
- 所有权限测试通过。

### Step 1.3 作业班级化

涉及文件：

- `app/models.py`
- `alembic/versions/*.py`
- `app/routers/assignment.py`
- `app/templates/teacher/assignment_form.html`
- `app/templates/teacher/assignments.html`
- `app/templates/student/assignments.html`
- `tests/test_assignment_permissions.py`

当前风险：

- 教师创建作业时可选择全站题目。
- 学生端展示所有作业。
- 学生可提交任意作业 id。

实现步骤：

1. 给 `Assignment` 增加 `class_id` 字段。
2. 生成 Alembic 迁移。
3. 教师创建作业页面只展示当前教师创建的班级。
4. 教师创建作业时必须选择班级。
5. 题目选择只显示当前教师创建的题目。
6. 学生作业列表只显示自己 `class_id` 对应的作业。
7. 完成作业前校验学生属于该作业班级。
8. 教师作业列表只显示自己创建的作业。

测试用例：

- 教师 A 不能把教师 B 的题加入作业。
- 学生 A 只能看到自己班级作业。
- 学生 A 不能通过伪造 id 完成其他班级作业。
- 教师 A 不能看到教师 B 的作业。

验收标准：

- 作业不再全站可见。
- 作业完成记录不会跨班写入。

### Step 1.4 题库归属校验

涉及文件：

- `app/routers/teacher.py`
- `tests/test_question_bank_permissions.py`

当前风险：

- 创建、编辑、导入题目时直接接受 `bank_id`。
- 没有确认该 `bank_id` 是否属于当前教师。

实现步骤：

1. 新增 helper：`get_owned_bank_or_none(db, teacher_id, bank_id)`。
2. 创建题目时，如果 `bank_id` 不属于当前教师，返回 400。
3. 编辑题目时同样校验。
4. 批量导入题目时同样校验。
5. 题库删除时只影响当前教师题库。

测试用例：

- 教师 A 可以把题放入自己的题库。
- 教师 A 不能把题放入教师 B 的题库。
- 教师 A 导入题目时不能使用教师 B 的 `bank_id`。

验收标准：

- 伪造 `bank_id` 无法跨教师污染题库。

### Step 1.5 班级成员一致性修复

涉及文件：

- `app/routers/classgroup.py`
- `app/routers/auth.py`
- `tests/test_class_membership_consistency.py`

当前风险：

- 教师可以按用户名把任意学生加入自己班级。
- 学生可能存在多个 `ClassMember`，但 `users.class_id` 指向另一个班级。

实现步骤：

1. 明确当前版本只支持学生一个主班级。
2. 注册时选择班级后，写入 `users.class_id` 和 `ClassMember`。
3. 教师手动添加学生时，如果学生已有其他 `class_id`，应提示不可添加或要求先移出原班。
4. 移除学生时同步清空 `users.class_id`。
5. 审核游客加入班级时，必须只允许审核到当前教师班级。

测试用例：

- 已在 A 班的学生不能被 B 班直接添加。
- 移出班级后 `users.class_id` 清空。
- 游客审核通过后只属于一个班级。

验收标准：

- `users.class_id` 与 `class_members` 不再互相冲突。

### Step 1.6 CSRF 和输入校验补齐

涉及文件：

- `app/routers/auth.py`
- `app/routers/teacher.py`
- `app/routers/student.py`
- `app/security.py`
- `tests/test_input_validation.py`

实现步骤：

1. `POST /logout` 增加 CSRF 校验。
2. 新增 `parse_int(value, default=None, min_value=None, max_value=None)` helper。
3. 替换所有直接 `int(form.get(...))` 的地方。
4. 非法数字输入返回表单错误，不返回 500。
5. 对 `difficulty`、`daily_goal`、`sort_order`、`class_id`、`bank_id` 设定范围。

测试用例：

- 无 CSRF 的 logout 被拒绝。
- 非数字 `class_id` 不触发 500。
- 非数字 `daily_goal` 不触发 500。
- 非法 `difficulty` 不触发 500。

验收标准：

- 用户输入错误只显示错误提示，不出现服务器错误。

## 阶段 2：数据可靠性和运维能力

目标：产品出问题时能发现、能恢复、能回滚。

### Step 2.1 数据库备份策略

实现内容：

- Render Postgres 开启定期备份能力，若免费库不支持长期可靠备份，应迁移到付费数据库。
- 每日导出关键数据：用户、班级、题目、作业、记录。
- 增加管理员手动导出入口。
- 编写恢复演练文档。

建议文档：

- `docs/backup-and-restore.md`

验收标准：

- 能从备份恢复到测试数据库。
- 恢复流程有人可以照文档执行。

### Step 2.2 日志与错误追踪

实现内容：

- 统一应用日志格式。
- 记录请求 id。
- 记录 500 错误堆栈。
- 记录登录失败、权限拒绝、导入失败、迁移失败。
- 可选接入 Sentry 或其他错误监控服务。

验收标准：

- Render Logs 能定位一次 500 的具体路由和错误。
- 导入失败能看到文件名、教师 id、失败原因。

### Step 2.3 健康检查和告警

实现步骤：

1. 扩展 `/health`，返回数据库连接状态。
2. 新增 `/health/db`，只给内部或管理员使用。
3. 部署后检查 `/health`。
4. 设置 Render 服务异常通知。

验收标准：

- 数据库不可用时健康检查能反映异常。

### Step 2.4 GitHub Actions CI

新增文件：

- `.github/workflows/ci.yml`

CI 步骤：

1. 安装 Python 3.12。
2. 安装依赖。
3. 运行 `pytest`。
4. 使用临时 SQLite 跑 `alembic upgrade head`。
5. 可选：运行 `python -m compileall app tests`。

验收标准：

- 每次 push 自动测试。
- CI 失败时不部署或至少阻止手动合并。

## 阶段 3：管理员后台

目标：让运营者能处理真实用户问题，而不是直接改数据库。

### Step 3.1 管理员角色完善

实现内容：

- 明确 `is_admin` 权限。
- 管理员后台入口只给管理员显示。
- 第一个教师自动成为管理员的逻辑移到显式初始化脚本或后台配置，避免启动时隐式改数据。

验收标准：

- 普通教师看不到管理员入口。
- 管理员能查看教师和班级列表。

### Step 3.2 用户管理

功能：

- 搜索用户。
- 重置密码。
- 禁用账号。
- 查看用户所属班级。
- 清理游客账号。
- 删除测试账号。

验收标准：

- 不需要进数据库即可处理常见账号问题。

### Step 3.3 操作审计

新增表建议：

- `audit_logs`
  - `id`
  - `actor_id`
  - `action`
  - `target_type`
  - `target_id`
  - `metadata`
  - `created_at`

需要记录：

- 教师邀请码修改。
- 用户密码重置。
- 班级删除。
- 学生移出班级。
- 题库批量导入。
- 作业删除或修改。

验收标准：

- 关键管理动作可追溯。

## 阶段 4：教师核心工作流优化

目标：让教师第一次使用就能完成闭环：建班、导入学生、导入题目、布置作业、看统计。

### Step 4.1 首次使用引导

页面建议：

- `/teacher/onboarding`

流程：

1. 创建第一个班级。
2. 导入或添加学生。
3. 创建题库。
4. 导入题目。
5. 布置第一份作业。
6. 查看统计入口。

验收标准：

- 新教师注册后能看到下一步提示。
- 未建班时不直接进入空白后台。

### Step 4.2 学生导入

功能：

- CSV 模板下载。
- 批量导入学生名单。
- 自动生成初始密码或邀请码。
- 导入预览。
- 错误行提示。

验收标准：

- 教师能一次导入一个班。
- 错误行不会导致整批失败。

### Step 4.3 题库导入增强

功能：

- 导入前预览。
- 行级错误提示。
- 重复题检测。
- 支持更新已有题目。
- 支持按题库、章节、难度筛选导入结果。

验收标准：

- 一份错误 CSV 不会造成部分不可知数据写入。
- 教师知道哪几行失败、为什么失败。

### Step 4.4 作业管理增强

功能：

- 作业草稿。
- 作业编辑。
- 作业撤回。
- 班级完成率。
- 未完成学生名单。
- 一键提醒。

验收标准：

- 教师能管理作业生命周期，而不是只能创建和查看。

## 阶段 5：学生学习闭环

目标：学生登录后清楚知道今天做什么，做完后知道哪里进步。

### Step 5.1 学生首页重构

首页模块：

- 今日待完成作业。
- 今日刷题目标。
- 最近错题。
- 薄弱知识点。
- 连续学习天数。

验收标准：

- 学生登录后不需要自己找入口。

### Step 5.2 错题复习机制

功能：

- 错题按掌握状态分类。
- 答对 N 次自动标记已掌握。
- 教师可查看班级高频错题。

验收标准：

- 错题不只是列表，而能进入复习闭环。

### Step 5.3 学习报告

功能：

- 学生个人报告。
- 班级报告。
- 家长可读的简版报告。
- PDF 导出优化。

验收标准：

- 报告能解释“学了什么、哪里弱、下一步做什么”。

## 阶段 6：合规和隐私

目标：让产品具备面对真实学生数据的基础合规能力。

### Step 6.1 隐私政策和用户协议

新增文档/页面：

- `/privacy`
- `/terms`

内容：

- 收集哪些信息。
- 为什么收集。
- 保存多久。
- 谁可以看到。
- 如何删除账号和数据。
- 未成年人使用说明。

验收标准：

- 注册页有协议和隐私政策链接。
- 用户必须确认后才能注册。

### Step 6.2 数据最小化

检查项：

- 是否真的需要学生真实姓名。
- 是否需要手机号。
- 是否需要学校全称。
- 是否需要家长信息。

原则：

- 能不用真实个人信息就不用。
- 能用班级内昵称就不用敏感信息。

验收标准：

- 注册字段保持最小。
- 后台导出不包含不必要个人信息。

### Step 6.3 数据删除和导出

功能：

- 学生账号删除申请。
- 教师删除班级数据。
- 管理员彻底删除用户。
- 导出个人学习记录。

验收标准：

- 用户数据生命周期可管理。

## 阶段 7：性能和扩展性

目标：小班使用稳定，逐步支持多班级、多教师。

### Step 7.1 查询优化

重点：

- 统计页 N+1 查询。
- 学生详情聚合查询。
- 题目浏览分页。
- 题库列表计数。

实现：

- 增加分页。
- 增加必要索引。
- 用聚合查询减少循环查询。

验收标准：

- 1000 道题、5000 条答题记录下页面仍能快速打开。

### Step 7.2 数据分页

需要分页的页面：

- 题库管理。
- 学生管理。
- 答题记录。
- 错题本。
- 通知列表。

验收标准：

- 大数据量下页面不会一次性加载全部记录。

## 阶段 8：发布、反馈和增长

目标：让产品能持续迭代，而不是一次性上线。

### Step 8.1 灰度试用

建议顺序：

1. 仅自己测试。
2. 1 位教师 + 1 个班级。
3. 3 位教师 + 3 个班级。
4. 小范围公开试用。

每轮收集：

- 注册成功率。
- 导入成功率。
- 作业完成率。
- 教师是否愿意第二次使用。
- 学生最常卡住的页面。
- Render 错误日志。

验收标准：

- 每轮试用后形成问题清单和下一轮修复项。

### Step 8.2 反馈入口

功能：

- 页面底部反馈入口。
- 教师后台反馈入口。
- 自动带上当前页面、用户角色、时间。

验收标准：

- 用户遇到问题能直接反馈。

### Step 8.3 正式发布准备

清单：

- 独立域名。
- HTTPS。
- 隐私政策。
- 用户协议。
- 数据备份。
- 管理后台。
- 监控告警。
- 回滚方案。
- 帮助文档。
- 客服联系方式。

验收标准：

- 不依赖开发者手动查数据库也能运营。

## 推荐执行顺序

### 第一周：安全和部署

- 修教师查看学生越权。
- 修作业全站可见。
- 修题库归属校验。
- 补 logout CSRF。
- 补数字输入校验。
- 加 GitHub Actions CI。

### 第二周：班级和作业闭环

- 作业绑定班级。
- 学生只看本班作业。
- 教师只用自己的题布置作业。
- 班级成员一致性修复。
- 补齐权限回归测试。

### 第三周：运维和管理员后台

- 数据备份文档。
- 管理员后台雏形。
- 用户搜索、重置密码、禁用账号。
- 审计日志。
- 健康检查增强。

### 第四周：教师体验

- 新教师 onboarding。
- 学生导入。
- 题库导入预览和错误行提示。
- 作业完成率和未完成名单。

### 第五周：学生体验

- 学生首页重构。
- 错题掌握状态。
- 学习报告。
- 通知和提醒优化。

### 第六周：灰度发布

- 找 1 个真实班级试用。
- 每天看日志和反馈。
- 修复阻塞问题。
- 形成正式发布清单。

## 每个阶段的完成定义

一个阶段只有同时满足以下条件才算完成：

- 代码已提交。
- 数据库迁移已验证。
- 自动化测试通过。
- Render 测试环境部署成功。
- 文档已更新。
- 有明确回滚方式。
- 至少覆盖一个失败路径测试。

## 近期最小可执行任务

如果只选最重要的 5 件事，建议按下面顺序做：

1. 修复教师跨班查看学生详情和 PDF 导出。
2. 作业增加 `class_id`，学生只看本班作业。
3. 教师创建作业时只允许选择自己的题目。
4. 创建/编辑/导入题目时校验 `bank_id` 归属。
5. 加 GitHub Actions，自动跑测试和迁移。

完成这 5 件后，项目才比较适合进入真实班级灰度试用。
